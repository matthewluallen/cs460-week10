Unauthenticated Coil Write

One weakness, traced the whole way: the SBOM flags its class in a dependency, the firmware's code reaches it, and the bus/network analyzer captures the outcome — a relay thrown by an anonymous, cleartext write.

2CWE · the weakness class

Cleartext control, with no one checked at the door

The same classes, as they apply to the controller itself:

CWE‑319
Cleartext Transmission of Sensitive Information
CWE‑306
Missing Authentication for a Critical Function

The firmware's own cwe command lists both. The CWE is the join: it carries the scanner's library finding onto the device's code.

↓ is there vulnerable code that reaches it?

3Code · the path that reaches it

The Modbus server writes coils for anyone

In firmware/src/modbus_tcp_server.cpp, the TCP server binds in the clear and the write‑coil path has no identity check:

// Modbus/TCP, port 502 — no TLS, no client auth (CWE-319, CWE-306) case FC_WRITE_SINGLE_COIL: // 0x05 coil = req.ref; value = (req.data == 0xFF00); io.coil_set(coil, value); // drives the I/O image directly — no caller check reply_echo(req); break;
↓ exercise it, and capture the wire

4Network capture · the write arrives

The write, in plaintext, from nobody

A pymodbus client over the emulated W5500 stack; tshark on lo. The write‑single‑coil frame, exactly as captured:

frame 10 · 127.0.0.1 → 127.0.0.1:502 · Modbus/TCP 00 03 00 00 00 06 01 05 00 00 FF 00 └tid─┘ └proto┘ └len─┘ └u┘ └fc┘└ref─┘└─data┘ Transaction id : 3 Unit : 1 Function : 0x05 Write Single Coil Reference : 0 Data : FF00 (ON) no TLS handshake precedes it · no credential field exists

↓ the scan carries the coil onto the physical bus

5Logic & bus · the write reaches the wire

The scan carries the coil onto the I²C bus

In RUN mode the scan reads that coil from the I/O image and writes the AW9523 relay register over I²C every cycle. The virtual tap captures it, and the same sigrok decoder the bus lab uses reads it back:

esp32_i2c_observe · /machine/soc/i2c0 · AW9523 relay register (0x59) before the write W 0x59 data=00 relays off after the write W 0x59 data=01 bit0 = relay0 ON sigrok-cli -i bus.vcd -P i2c → Address write: 59 · Data write: 01

No ladder rung set that bit — a network coil write did, and it is now on the physical bus, the same trace a bench logic analyzer would capture.

↓ which the bus analyzer shows as a physical outcome

6Outcome · the physical result

Relay 0 closes

AW9523 0x59 · relay0 = ON

The same coil the scan drives from the ladder — now thrown by an anonymous network write. In i2c-analyzer.html it appears as a W 0x59 on the relay lane.

Finding

The scanner proved the class is present (CWE‑295 / CWE‑522 in shipped libraries). The code review found the path (an unauthenticated FC05 handler on a cleartext port). The network capture proved the entry (a readable, anonymous coil write); the I²C capture proved it reached the wire (the scan's W 0x59 relay‑register write, decoded by the same sigrok flow); and the analyzer proved the consequence (relay0 actuates). What the SBOM raised as a question, the analyzer answered — through the logic, down to the bus. Next observation that would change the verdict: put the write behind auth or TLS and re‑capture — the frame should no longer land, and W 0x59 should stay 00.

Captured on the StampLC QEMU twin · pymodbus → tshark on lo:502 · reproduce with bus-analysis + sbom/cwe_bridge.py. CVE/CWE from a grype scan of the dependency sample; frame bytes are the live capture.
