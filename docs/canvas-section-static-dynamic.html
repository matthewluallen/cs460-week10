Signal Journey — follow one byte through five lenses

If you have never opened Wireshark, a disassembler, or a logic analyzer before, start here. Signal Journey takes a single command and shows the same value as it changes form across five lenses — Wire (Wireshark bytes on port 502) → Code (the firmware parsing those bytes, with a "Deeper" view into the disassembly) → Logic (the coil in the ladder) → Bus (sigrok/PulseView decoding the I²C write to the relay chip) → Physical (the relay closing). Each lens has a plain "what is this tool?" note.

Three scenarios teach three different ways an output can move — and which lenses catch each one:

  • NORMAL — a legitimate Modbus write. All five lenses agree. This is the baseline you need before you can recognize a lie.
  • HIDES — a memory-corruption force (CWE-787). The network capture and the audit log go dark; the bus and the physical relay still fire. If you only watch the network, you miss it entirely.
  • LIES — a phone-sensor spoof (false-data injection). The value is on the wire, in the log, and in the logic — all consistent, all attributable — and all wrong. You catch this with an independent check, not by watching bytes move.

MITRE: CWE-787 (out-of-bounds write) / CWE-345 (insufficient verification of data authenticity); ATT&CK for ICS T0835 Manipulate I/O Image, T0856 Spoof Reporting Message; D3FEND — monitoring that reaches the bus and the physical output, not just the network.

Provenance Studio — which source line did this event come from?

The firmware records every audited output change through plc_log(WriteSource, …), served live at /api/log. Provenance Studio puts that live event stream beside the exact firmware source line that emitted each event — click an event and see the code, the WriteSource, and any CWE. The teaching moment is the provenance gap: a coil that changes with no matching log entry, because the memory-corruption force bypasses the audited write path. The absence in the log is the detection.

From the binary back to the running PLC — binwalk, Ghidra, and the static↔dynamic bridge

Part 6 pulled the shipped image apart statically — esptool image-info, strings (the baked-in admin:openplc credentials, CWE-798), binwalk (embedded PEM keys and certificate), and Xtensa objdump. The next step is to tie that static picture to what the controller is doing right now. Every event in Signal Journey and Provenance Studio names the function and load address it came from — the exact target to open in Ghidra on firmware.elf (whose Xtensa loader reads this image natively, with full DWARF source lines). So a live WRITE coil on the wire resolves to ModbusTCPServer::fc_write_single_coil @ 0x42037480, and you can walk from the packet to the decompiled function in one move.

These addresses are re-derived from the firmware's DWARF on every build (a PlatformIO post-build step), so they stay correct as the firmware changes — you are never reading a stale map.

Your phone as the sensor — and the attacker

On the MQTT phone-sensor bridge (the QR page), each sensor you share now has two controls that make you the field instrument and the adversary. Transmit ON/OFF: turn it off and the PLC ages the reading out — an availability attack; watch what your logic does when an input it trusts simply disappears. Override (real / spoof): drag the slider and your phone publishes a value you chose while the plant believes it — an integrity / false-data-injection attack; the card reads "SPOOFED 20 (real ≈ 512)," because the phone knows it is lying and the wire does not.

CYBER-INFORMED ENGINEERING — don't trust a single sensor. Every value entering control logic is a claim, not a fact. A safety-critical decision needs redundant, independent, or physically-bounded measurement, so that one phone (or one compromised transmitter) cannot talk the plant into the wrong state. The graded exercise for this is Part 5.5 — You are the sensor, and the attacker.
