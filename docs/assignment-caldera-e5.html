Extension E5 · Automate the attack with CALDERA (red vs blue)

Builds on Part 8 / E3 (the phone-sensor attack) and pairs with E4 (the detector it tests). Runs in the stations stack; no hardware. You used CALDERA on the wind farm in Module 4 (Week 8) — here it is on the controller you have been attacking by hand.

Why this part exists. In E3 you spoofed the phone sensor by clicking the phone page. A real adversary does not click — they automate, and they had to get in first. E5 runs the exact same forgery as a MITRE CALDERA operation, and it makes the step every other Part skips explicit: initial access. Every Part so far assumed the attacker was already on the plant network; here you see how the agent got there, and you get the attacker’s own event log of the whole chain.

The setup. Bring up the stations stack including the C2 (docker compose -f stations/docker-compose.yml up --build; the first build is slow — it builds CALDERA and its UI). Then run the two steps below. Full walkthrough and the kill-chain diagram: caldera/README.md.

Attack A — Initial access: how the agent got there

The C2 agent does not appear on the engineering workstation by itself. In the real world it rides an earlier link in the chain — a USB stick left in a parking lot, or a phishing email attachment an engineer opens. The dropper script stands in for that delivery: it fetches the agent from the C2 and runs it.

docker compose -f stations/docker-compose.yml run -d --rm --name cs460-dropper engineer /app/deploy-sandcat.sh
  • SHOW — the dropper fetching and launching the agent, and the agent checking in to the CALDERA server (the UI at :8888, login red/admin, or the agents list).
  • SAY — which real delivery you are emulating and what it assumes (a human plugged in a stick, or opened an attachment). Nothing here exploits anything — the exploitation already happened, upstream.
  • WHY — every attack in this lab starts after this step. If initial access is where the chain really begins, what does that say about defending only the last gate?

Maps to: ATT&CK for ICS T0847 Replication Through Removable Media (CAPEC-452 Infected Hardware) or T0865 Spearphishing Attachment (CAPEC-163 Spear Phishing); then T0863 User Execution + T1105 Ingress Tool Transfer.

Attack B — The operation: the kill chain and its event log

With an agent in place, run the operation. CALDERA executes the adversary profile step by step and records each one.

docker compose -f stations/docker-compose.yml exec caldera python3 /usr/src/app/run-scenario.py
  • SHOW — the event log: discover the broker, spoof a sensor reading, spoof a button (command). Point at the forged phone/<id>/… on the wire (the capture station) and the controller acting on it (mqtt status / the HMI tile) — the same consequence as E3, now automated.
  • SAY — what the automation adds over the manual E3 attack: repeatability, the technique IDs, and a record an analyst can read. Name each kill-chain stage and its technique.
  • WHY — the event log is the attacker’s view; the defender gets the capture and the controller state. Which lens would a blue team actually have?

Maps to: ATT&CK for ICS T0846 Remote System Discovery → T1692.002 Unauthorized Message: Reporting Message (formerly T0856) → T1692.001 Unauthorized Message: Command Message (formerly T0855) → T0835 Manipulate I/O Image. Tooling: CALDERA with a custom MQTT ability (caldera-ot has no MQTT plugin).

Attack C — Red vs blue: run it against the E4 detector

If you built E4, this is the payoff. Start the detector (ai-detector/detect.py) against the broker, then run the CALDERA operation again and watch the detector’s verdicts. The naive spoof is flagged; the crafted spoof (edit the fact source to a gentle, in-range value) slips past the model and is caught only by the accelerometer cross-check.

  • SHOW — the CALDERA operation running on one side and the detector’s ai/<id>/verdict on the other: which steps alarm, which do not.
  • SAY — the red and blue views of the same event, and where they disagree.
  • WHY — automation lets the attacker tune the spoof against the detector quickly (that is an ATLAS move, AML.T0015/T0043). Detection raises the attacker’s cost; it does not make the sensor trustworthy.

CYBER-INFORMED ENGINEERING — assume the attacker gets in. The kill chain starts with initial access, so a single gate at the end is not a plan — consequence reduction has to hold even after the adversary has an agent on the network and can automate. Where in your design does one compromised workstation reach something that matters, and what bounds the damage once it does?
