Extension E4 · Attack the AI that watches the sensor

Builds on Part 8 / E3 (phone-as-sensor false-data injection). No extra hardware — the same phone stream, now with a machine-learning anomaly detector watching it. Everything runs in the Codespace; the core needs no broker. Pairs with the Threat Map (ATLAS column) in the Logic Studio toolbar.

Why this part exists. In E3 you defended one trusted sensor with a rule you wrote by hand. The next thing a real OT team reaches for is a model that learns what normal looks like. But the moment a model makes a decision, the model is a new attack surface — the one MITRE ATLAS (atlas.mitre.org, the adversarial-AI companion to ATT&CK) catalogs. Here you build that detector, then attack it.

The setup. pip install -r ai-detector/requirements.txt. Record a normal-operation baseline from your phone (python ai-detector/record.py --seconds 300 --out ai-detector/out/baseline.jsonl) or simulate one (python ai-detector/phonesim.py --scenario baseline --out ai-detector/out/baseline.jsonl) — share both Motion and Orientation so the accelerometer is in it. Train both profiles: train.py --profile vuln (model only, one pickle, learns online) and, after vendor.py keygen + approve-dataset, train.py --profile secure (gate + model + accelerometer cross-check; signed, frozen). The detector raises an alarm on ai/<id>/verdict; it never writes the controller — keeping AI out of the actuation path is the point, not a limitation.

One command proves every property below offline: python ai-detector/verify.py (also python assessment/verify-lab.py E4). Drive any attack live with phonesim.py --scenario <name> --publish 127.0.0.1:1883 while detect.py runs. Each check names its ATLAS 2026.10 ID.

Attack A — Evasion: a spoof the model can’t see

First try the blunt E3 move: slam the reported tilt to a wild value (--scenario naive-spoof). The model flags it — and the secure profile’s gate rejects it before the model even runs. Now do better: follow the real tilt until it nears the alarm limit, then slide the reported value gently (a normal rate) back to a perfectly ordinary tilt and hold it there (--scenario crafted-spoof). Every value you report is one the model has seen a thousand times, so the model alone never alarms — while the real phone is tipped past the limit.

  • SHOW — detect.py --profile vuln --replay on your crafted capture: the hidden window stays OK. Then the same capture under --profile secure: the accelerometer cross-check fires (fusion: reported tilt is N° from the tilt gravity implies).
  • SAY — which signal betrayed the spoof. You changed what the phone reported; you did not change the gravity its accelerometer still feels. That gap is the detection.
  • WHY — a learned model only knows the distribution it was shown; an in-distribution lie is invisible to it. Detection came from an independent physical channel, not a smarter model.

Maps to: ATLAS AML.T0015 Evade AI Model via AML.T0043.003 Craft Adversarial Data: Manual Modification; tilting/covering the real phone is AML.T0041 Physical Environment Access; the defence is AML.M0009 Multi-Sensor Fusion (and the gate, AML.M0015).

Attack B — Integrity of the model itself: poison or erode it

Two ways to make the model call your value normal. Poison the baseline (--scenario poisoned-baseline): publish your target tilt while the recording is being made, so “normal” is defined to include it; later that tilt passes (poison-target). Erode it (--scenario erode): if the model learns online (detect.py --adapt), drift the reported value down so slowly that each small step is accepted and folded into the next baseline — over ~17 minutes it re-centres onto you.

  • SHOW — a -30° reading alarming on a clean model but accepted after a poisoned baseline; or the online model’s alarm rate decaying to near zero as it drifts (verify.py E4-07 / E4-09 print both).
  • SAY — which did it: you changed the training data, not the input. The model is exactly as designed; its idea of normal is what you corrupted.
  • WHY — a model is only as trustworthy as its data and its re-training policy. Whatever is on the wire while you record becomes truth.

Maps to: ATLAS AML.T0020 Training Data Poisoning, AML.T0031 Erode AI Model Integrity; the defences are AML.M0007 Sanitize Training Data + AML.M0025 Maintain AI Dataset Provenance (the secure profile trains only on a reviewed, hash-approved recording and drops uncorroborated frames).

Attack C — Supply chain: own the model, own the decision

You never have to beat the model if you can replace it. The detector loads its model from a registry — the same shape of update source as the firmware OTA in Parts 6–7. attack.py swap-model drops in a model whose alarm can never fire; attack.py evil-pickle drops in a “model” that runs code the moment it is loaded (the vuln profile unpickles it; proof lands at /tmp/aidet-model-ran-code). Query the /score endpoint first (attack.py probe) to see how an exposed raw score hands you a free optimization oracle.

  • SHOW — the vuln loader accepting the swapped/evil model (and the marker file appearing); the secure loader REFUSEDing it (signature does NOT verify / SHA-256 does not match); aibom.py --check reporting the drift.
  • SAY — you never touched a reading or the training data — you replaced the artifact. An unsigned model file is not just untrusted data; a pickle is untrusted code.
  • WHY — this is Part 7’s kill switch, one layer up: whoever controls the model source controls every decision it makes.

Maps to: ATLAS AML.T0010.003 AI Supply Chain Compromise: Model Repository, AML.T0018.000 Poison AI Model, AML.T0011.000 Unsafe AI Artifacts, AML.T0040 AI Model Inference API Access; defences AML.M0013 Code Signing + AML.M0014 Verify AI Artifacts + AML.M0023 Maintain an AI Bill of Materials (Part 5), and AML.M0004 / M0002 for the query oracle.

Then defend it — and name what still gets through

The secure profile is those controls; turn one off and watch the matching attack land. One honest limit remains: the accelerometer cross-check compares two channels from the same phone. Forge both (--scenario forge-all) and fusion is defeated — because real corroboration needs an independent sensor, not a second reading from the same source. State that residual risk; don’t hide it.

CYBER-INFORMED ENGINEERING — the detector’s verdict is one more claim. A model adds work for the attacker and buys detection; it does not make a single unauthenticated sensor trustworthy, and it must never sit in the actuation path. Adding AI to defend a system adds a system to defend. Where in your design would a model’s verdict decide something that matters — and what independent check guards the model itself?

What to submit

  • One evasion (Attack A): Show / Say / Why, with the capture, and the channel that caught it — mark which part is observation and which is inference.
  • One integrity attack on the model itself (Attack B or C): Show / Say / Why, and the specific secure-profile control that stops it.
  • Your AI-BOM (aibom.py) and one sentence on what syft listed that it did not — the model and its training data.
  • One paragraph on the residual risk: what a patient attacker still gets through, and why “add a detector” is not the same as “trust the sensor.”
